# Changelog: GitHub panel

## Unreleased

### Fixed

- **The panel follows your pane again, and sizes itself, under a Rex that sets only `REX_BLOCK`.** Rex 0.1.0-preview.23 no longer sets `REX_SESSION` in a pane, and the panel made no Rex call without it: it stayed on the folder it opened in, kept no width, and Resolve, Review and Auto-pilot said to open the panel in Rex. It now asks Rex once for the session holding its own pane (`rex api call -s $REX_BLOCK session.view`) and uses that, and still takes `REX_SESSION` when Rex sets it.

## 0.1.0 (2026-11-25)

The first public release of the GitHub panel for Rex, ported from [herdr-github](https://github.com/luongnv89/herdr-github) 0.4.0. It also brings the panel up to date with [herdr-github](https://github.com/luongnv89/herdr-github)'s unreleased changes after 0.4.0 ([luongnv89/herdr-github#18](https://github.com/luongnv89/herdr-github/issues/18), [#20](https://github.com/luongnv89/herdr-github/issues/20), [#25](https://github.com/luongnv89/herdr-github/issues/25)).

### Added

- The panel for Rex, ported from [herdr-github](https://github.com/luongnv89/herdr-github) 0.4.0: the repo's open pull requests (or merge requests) and issues from `gh` or `glab`, in a pane on the right of the tab.
- `rex-github.lua`: a `github_panel` action for `init.lua` that opens the panel beside the focused pane or closes it. The panel is the block labelled `rex-github`, so nothing is kept on disk to find it again.
- The panel follows the focused pane of its tab through `rex api call`, and reads that pane's folder from its foreground program.
- `install.js`: adds the panel and a key (`cmd+shift+g`, or the first free fallback) to `init.lua`, checks the result with `rex config check`, puts the old file back if the check fails, and reloads the config. `--remove` takes it out again.
- Import mcc profiles into the profile list ([#63](https://github.com/luongnv89/rex-extensions/issues/63)). When mcc is installed (found through `$MCC_BIN` when it is the full path of an executable file, else the `PATH`, or `~/.local/bin`, `~/.cargo/bin`, `/opt/homebrew/bin` and `/usr/local/bin`), the settings' **Profiles** tab shows **+ Import** in the header (in a pane 32 columns or wider, so **⚙ Settings** stays whole) and `i` imports: the panel lists mcc's Claude Code profiles from `mcc usage --json-v2`, without Devin's, tagging mcc's default and the ones imported already. Space (or **Mark**) marks profiles and `a` marks every one not imported yet, so several import at once, saved in one write; one that fails is named with its reason and stays marked, while the others are saved. Enter or **Import** (**Import N** with N marked) adds, for each, a **Claude Code via mcc run** profile named `mcc <name>` that starts that mcc profile with `mcc run --profile <name> --`, with the `model` and `effortLevel` of its own `settings.json`, in the folder `mcc env -q --shell bash <name>` names; a value it can't hold, such as `opus[1m]`, is left at the harness default, which still starts the profile's own. It can then be assigned or chosen in the profile menu like any other; Resolve and Review look for its skills in its own folder, and **Test** checks that mcc finds it. Without mcc, the settings are as before. Imported profiles are kept in the profiles file as version 7, written only while a profile has one, so a file without them drops back to the lowest version that holds the rest, byte for byte. A panel or herdr-github from before version 7 shows such a file read only, so it never drops an imported profile by saving; an older panel can still start an imported profile, but as a plain `mcc run --` with the repo's mcc profile, so update every panel that uses the file together. Resolve, Review and **Test** now also find mcc off a thin `PATH`, in those folders.
- Button labels of your own for **Resolve**, **Review** and **Auto-pilot**, so a button says what your prompt does. The settings' **Buttons** tab shows each button as it reads (`Resolve #N`, `☑ Auto-pilot`) beside its prompt, and its editor's **Label** field sets it (see [#70](https://github.com/luongnv89/rex-extensions/issues/70) below); empty, **Use default** or ctrl-r on that field brings back the button's own name. The label goes on each issue's **Resolve #N** button, each pull request's **Review #N** and the header's **☑ Auto-pilot**. It also goes in the profile menu's title, the notice on leaving Auto-pilot, and the names the settings give the action. The prompt, profile and pane label (`resolve-12`) don't change, and neither do **▶ Start** and the key hints. A label is up to 24 characters on one line, with no backslash or control characters, and no invisible characters. Labels are kept in the profiles file as version 6, written only while a button has one, so a file without them drops back to the lowest version that holds the rest, byte for byte. A panel or herdr-github from before version 6 shows such a file read only.
- Launch arguments of your own on an agent profile ([#48](https://github.com/luongnv89/rex-extensions/issues/48)). The profile form has an **Args** field: flags typed on one line, separated by spaces, such as `--dangerously-skip-permissions` for Claude Code or `-c model_reasoning_effort=high` for Codex. They are passed to the harness as they are, each one word with no shell, after the profile's model and thinking flags and before the prompt (before Devin's `--` and OpenCode's `--prompt`). Clear the field to remove them. A word can't be `--` on its own or hold a backslash or a control character, and a profile holds up to 16 words of up to 200 characters; a word that can't be used shows why under the field. Args longer than the pane show their end while you type in them, after a "…", so what you type and what backspace takes stay in view; the same goes for Name and Id. **Test** doesn't check them, and says they are checked only when the agent starts. A profile without them starts exactly as before. They are kept in the profiles file as version 5, written only while a profile has some, so a file without them drops back to the lowest version that holds the rest, byte for byte; a panel or herdr-github from before version 5 shows such a file read only.
- A **Devin** harness for agent profiles, for Cognition's Devin CLI. Resolve, Review and Auto-pilot start `devin -- <prompt>` in the new pane, or `devin --model M -- <prompt>` with a model; the prompt follows `--`, since Devin reads a word before it as a path to open in Devin Desktop. The form offers Devin's current families (`swe-2`, `claude-opus-5.5`, …), and `+` adds any family, alias or model `devin models list` prints. It doesn't offer `adaptive`, which routes each request to a model Devin picks, such as `swe-2-max`, rather than the one the profile names ([#49](https://github.com/luongnv89/rex-extensions/issues/49)). A Devin profile takes no thinking level: it is part of the model's name, as in `claude-opus-5-5-high`. The profile form's **Test** runs `devin --version` and, with a model, `devin models list --process-model in-process`, and checks the model is listed. The panel also recognises a pane running `devin` as your agent, and looks for the IDD skills in Devin's own folders too (`~/.config/devin/skills`, `~/.config/cognition/skills`, a repo's `.cognition/skills`). herdr-github doesn't have this harness yet, so it, and a panel from before this, shows a profiles file with a Devin profile read only.
- A **Test** button in the profile form, and ctrl-t, to check that a profile works before you save it or start an agent with it ([#43](https://github.com/luongnv89/rex-extensions/issues/43)). It runs, in the repo's folder, the harness's command with `--version`, for mcc also `mcc env -q --shell bash`, and with a model `pi --list-models`, `opencode models` or `devin models list --process-model in-process`, each stopped after 15 seconds, and never with a prompt. The settings then say in green what passed, or in red the first check that failed and why: not on your `PATH`, a command that failed or didn't answer, no mcc account for the repo, or a model Pi, OpenCode or Devin doesn't list. A field the profile can't take shows its reason under it. Testing saves nothing, adds no model and opens no pane; a result goes once you change the harness, model or thinking level, and one that comes back after you changed them, or left the form, isn't shown. The form's key hints say `^T test`.
- A setting to choose whether merging a pull request deletes its branch ([#39](https://github.com/luongnv89/rex-extensions/issues/39)). The settings have an **After a merge** row on their **Merging** tab: **Delete the branch**, the default, or **Keep the branch**; `e`, enter or its **Change** button switches it, and it's kept in `~/.local/state/rex-github/merge`, so it stays after a restart. In the mode that deletes, once GitHub says the pull request merged, the panel deletes its branch on GitHub with `gh api -X DELETE` (and then tidies your checkout: see [#41](https://github.com/luongnv89/rex-extensions/issues/41) below). It keeps a fork's branch, the branch merged into and the repo's default branch, and says why; in a repo that deletes merged branches itself, it leaves that to GitHub. A branch already gone counts as deleted, and a delete that fails is said in red without undoing the merge. On GitLab, `glab mr merge` gets `--remove-source-branch`. A merge that fails, waits for checks or a queue, or can't be read deletes nothing. The Merge question now names the mode, as in `(squash, then delete its branch)`.
- Back on an up-to-date main after a merge that deletes the branch ([#41](https://github.com/luongnv89/rex-extensions/issues/41)). Once the forge says the pull request merged, the panel runs `git` in the repo's folder: on the merged branch with nothing uncommitted, `git switch` to the repo's default branch; on the default branch, `git pull --ff-only --prune`, else `git fetch --prune`; and `git branch -D` for the merged branch's local copy, only while it isn't checked out and its tip is still the commit that merged. The merge's notice adds each step, as in `Merged #12 and deleted its branch b12; switched to main; pulled main; deleted the local b12`. On the merged branch with uncommitted changes, or with no default branch known (GitLab, where no local branch is deleted either), the checkout stays where it is and the notice says why; a default branch with uncommitted changes isn't pulled; a step that fails is said in red with git's `fatal:` or `error:` line, and the merge stands. `git` runs with `GIT_TERMINAL_PROMPT=0` and without a terminal, so neither git nor ssh prompts over the panel. The mode that keeps the branch leaves the checkout alone, and the panel still never passes `--delete-branch` to `gh`.
- A key for every button, so the panel works without a mouse ([#37](https://github.com/luongnv89/rex-extensions/issues/37)). `m` presses the selected pull request's **Merge #N** and `c` the selected issue's **Close #N**; both still ask first, and `y` confirms, at once rather than after the 0.4 seconds a second click waits. Pressing `m` or `c` again leaves the question as it is, so a key held down never merges or closes, and any other key still takes the question back. `c` does nothing in Auto-pilot mode, where Close steps aside. In a button's editor, ctrl-r is **Use default** for the field you are on while it holds a custom value. `?` lists every key of the view you're in (the lists, Auto-pilot, the profile menu or the settings), and `?`, esc, `q` or a click closes the list; no other key reaches the view under it. The key hints now say `? keys`, early enough to stay in view in a 36-column pane, and a wide pane also names `m merge #N` or `c close #N` for the selected row. Auto-pilot's narrowest key hints end with a bare `?`. The Merge and Close notices now name `y`. In typing fields `?` is still text.
- Labels on the header's buttons. They now sit on a line of their own under the repo's name, as **☑ Auto-pilot**, **⚙ Settings**, **↻ Refresh** and **↗ GitHub** (or **↗ GitLab**), and a click on a label presses its button. In a narrower pane the labels drop from the right, leaving those buttons' icons. In a pane too narrow for even the first label, or shorter than 12 lines, the header is one line again, with the bare icons after the repo's name as before.
- Choose a model for an OpenCode profile. OpenCode's interactive command has no `--model` flag, so with a model the panel starts it as `env OPENCODE_CONFIG_CONTENT={"model":"M"} opencode --standalone --prompt <prompt>`: the model goes in a one-line OpenCode config, and `--standalone` gives that pane OpenCode's own server, since the background service doesn't read the variable. Its sessions are still listed with the others. Without a model, OpenCode starts as before. The extension ships no OpenCode models: `+` on **Model** adds yours, as `provider/model` from `opencode models`. The notice now says OpenCode ignores only a thinking level. A panel from before this shows a profiles file with OpenCode models read only.
- Auto-pilot several issues at once ([#31](https://github.com/luongnv89/rex-extensions/issues/31)). On GitHub's issues, a `☑` button in the header, before `⚙`, or `p`, enters Auto-pilot mode: every issue row shows a checkbox in place of its icon, and its Resolve and Close buttons step aside. A click on a row, or space or `x` on the selected one, checks or unchecks it. The key hints give way to a **▶ Start** and **✕ Cancel** bar, shown only in the mode: Start is dimmed and does nothing until an issue is checked, then reads **▶ Start N**. Start, or enter, runs one agent, in one new pane labelled `autopilot-12-15`, on exactly the checked issues, in the list's order: by default the IDD `auto-pilot` skill, as `/auto-pilot --issues 12,15` (`/idd:auto-pilot` from the plugin) for Claude Code and "Use the auto-pilot skill with --issues 12,15." for other agents, with the profile Resolve starts (the profile menu opens first when you have profiles of your own). Once the agent runs, the mode ends and nothing is checked; Cancel, `☑`, `p`, esc and `q` leave it too, without closing the panel, as do the pull requests list and another repo, with a notice saying how many issues that unchecked. The bar's key hints start with `⏎ start`; in a narrow pane they shorten to `⏎▶ · ␣☑ · q✕`, so a 36-column pane still shows the keys that start, check and cancel. An issue that leaves the list is unchecked. Like Resolve and Review, Auto-pilot can send a prompt of your own, set in the settings view's **Buttons** tab, with `{numbers}` where the checked issues' numbers go (`12,15`); one longer than 500 characters with them filled in is refused before anything runs. A custom Auto-pilot prompt is kept in the profiles file as version 4, written only while you have one, so a file without one drops back to the lowest version that holds the rest, byte for byte; a panel or herdr-github from before version 4 shows such a file read only.
- A **Close #N** button on every issue row, on GitHub and GitLab, to close an issue without resolving it ([#27](https://github.com/luongnv89/rex-extensions/issues/27)). On GitHub it sits next to the Resolve button (on a line of its own in a narrow pane); on GitLab it's on a line of its own. Like Merge, the first press only asks: the button turns red and reads **Confirm close #N**; a second press closes that issue, and only that one, with `gh issue close` or `glab issue close`, and starts no agent or pull request. Any other key or click, including esc and `q`, takes the question back, and a second press within 0.4 seconds of the first only keeps the question. While the close runs the button reads **Closing #N…**; `Closed #N` takes the issue out of the list, and a refresh already running doesn't bring it back; a refused close shows the CLI's reason in red and keeps the issue.
- Choose a profile's model from a list ([#24](https://github.com/luongnv89/rex-extensions/issues/24)). In the profile form, **Model** is now a choice: ←/→ or space step through **harness default**, then the models the extension ships for the selected harness (Claude Code via `mcc run`, Claude Code, Codex, Pi, Mistral Vibe and Devin; none for OpenCode), then the ones you added. `+` on **Model** adds a model that isn't listed, checked by the same rule as before, and `-` removes one you added. Added models are kept per harness in the profiles file as version 3 (`customModels`), written only while you have one, so a file without one drops back to the lowest version that holds the rest; a panel or herdr-github from before version 3 shows such a file read only. A profile whose model is in neither list loads, shows and starts as before.
- A **Mistral Vibe** harness for agent profiles. Resolve and Review start `vibe <prompt>` in the new pane. A model on the profile goes in the `VIBE_ACTIVE_MODEL` environment variable, as `env VIBE_ACTIVE_MODEL=M vibe <prompt>`, since Vibe's `--model` flag works only in headless mode; an alias Vibe doesn't know starts its default model. A Mistral Vibe profile takes no thinking level: Vibe sets it per model in its own config. The panel also recognises a pane running Vibe, whose program is `vibe-rs`, as your agent, and opens the new pane beside it. herdr-github gets the same harness; a herdr-github without it shows a profiles file with a Mistral Vibe profile read only.
- A **Resolve #N** button under every issue and a **Review #N** button under every pull request, on GitHub. Each acts on its own row; `a` acts on the selected one. There are no Resolve or Review buttons on GitLab, since both skills work through `gh`.
- A **Merge #N** button on every pull request row, next to its Review button (on a line of its own in a narrow pane), and a **Merge !N** button on every GitLab merge request row ([#13](https://github.com/luongnv89/rex-extensions/issues/13), from [herdr-github#51](https://github.com/luongnv89/herdr-github/issues/51)). The first press only asks: the button turns into **Confirm merge #N** and the notice names the merge method; a second press merges that pull request, and only that one, with `gh pr merge` or `glab mr merge`. Any other key or click, including esc and `q`, takes the question back, and a second press within 0.4 seconds of the first, as in a double click, only keeps the question. On GitHub the method is the repo's: squash when it's allowed, else a merge commit, else rebase; when the repo allows none, or `gh` doesn't say, the press says why and merges nothing. On GitLab the project's own method applies. The merge passes the head commit the list read (`--match-head-commit`, `--sha`), so it's refused when the branch moved since. It never passes `--delete-branch` to `gh` (for the branch a merge deletes, and GitLab's `--remove-source-branch`, see [#39](https://github.com/luongnv89/rex-extensions/issues/39) above); the repo's own setting to delete head branches after a merge, or a merge request's **Delete source branch** box, still applies. The panel then reads the pull request's state: `Merged #N` takes it out of the list, and a refresh already running doesn't bring it back; a merge left waiting in a merge queue or for checks says so and keeps it; a refused merge shows the CLI's reason in red. While the merge runs, the button reads **Merging #N…** and a press on it does nothing; when the pull request stays in the list, refused or waiting, it reads **Merge #N** again ([#20](https://github.com/luongnv89/rex-extensions/issues/20)).
- Agent profiles. A profile has a name, an id, a harness (Claude Code via `mcc run`, Claude Code, Codex, Pi, OpenCode, Mistral Vibe or Devin) and optional model, thinking level and launch arguments; an empty model or thinking level leaves the harness's own default. Resolve and Review each get their own profile. Models with shell characters or brackets (such as `opus[1m]`) are refused. OpenCode has no thinking flag when it starts, so the panel says it ignores a thinking level.
- A **Settings** view (`s`, or **⚙ Settings** in the header) to add, edit, delete and assign profiles, edit each button's label and prompt, and choose what a merge does with its branch, from the keyboard and the mouse. A profile's id is dim and the actions it starts are in the accent color; an id or a description that only repeats the profile's name isn't shown again, so the default profile no longer says "Claude Code via mcc run" twice. It reads and writes `~/.config/rex-github/profiles.json`, in herdr-github's format, and never overwrites a change made meanwhile, nor a file it can't read or that holds a profile it can't use.
- Choose the profile when you start Resolve or Review, from the keyboard alone as well as the mouse, as on a phone over remote access, where taps on the buttons may not reach the panel ([#28](https://github.com/luongnv89/rex-extensions/issues/28)). With one or more profiles of your own, a **Resolve #N** or **Review #N** click opens a menu of every profile under the button clicked (above it when there's no room), while `a` opens it at the bottom of the panel, just above the notice and the key hints, so it's in view on a phone, which shows only the bottom of the pane. The menu lists the built-in **Claude Code via mcc run** first, with the action's assigned profile highlighted. Enter or a click starts the one chosen; esc, `q` or a click elsewhere closes the menu and starts nothing. The key hints start with what `a` acts on, such as `a resolve #12` or `a review #34`, so it survives a narrow pane's cut, and the menu's hints name `j`/`k` and `q` as well as the arrows and esc, with a shorter form that keeps a key that cancels in view. With only the built-in profile, the button or `a` starts it right away.
- Custom prompts for Resolve and Review. Each action can send a prompt you write, with `{number}` where the number goes, instead of the IDD skill's; left empty, it sends the skill's prompt as before. The prompt is the last word of the agent's command line, and a custom prompt starts the agent even when the IDD skills aren't installed. Set it in the settings view's **Buttons** tab.
- With bracketed paste, pasting types the text into the prompt or the form field being edited, with its line breaks as spaces; nothing pasted is read as a key. In a terminal without bracketed paste, the paste arrives as keys: text after the line break that saves the prompt or form is dropped rather than run as commands, while outside a field it is indistinguishable from typing.
- With mcc, the skills are looked up in the Claude Code folder `mcc env` names for the repo. For mcc, the panel says it opened the pane rather than that Claude Code started, since mcc may first ask something, such as about a usage limit.

### Changed

- The settings view shows its areas as three tabs, **Profiles**, **Buttons** and **Merging** ([#67](https://github.com/luongnv89/rex-extensions/issues/67)). Settings opens on **Profiles**. Only the tab showing has its settings drawn, and it's inverted in the strip under the header. `1` to `3` open a tab, tab, `→` or `l` the next one (going round from **Merging** to **Profiles**) and shift-tab, `←` or `h` the previous one, and a click on a tab's name opens it. While `d` is asking whether to delete a profile, any of these keys or clicks takes the question back and deletes nothing. `↑`/`↓` and the mouse wheel stay within the tab, stopping at its first and last row. **+ New** and **+ Import** show in the header on **Profiles** only, though `n` and `i` still work from every tab. Every tab is named down to 28 columns; narrower still, the tabs not showing keep only their number. Changes are still saved at once, so they stay after switching tabs or closing the settings.
- Each button's label and prompt are edited together, on the **Buttons** tab ([#70](https://github.com/luongnv89/rex-extensions/issues/70)). Each **Resolve**, **Review** and **Auto-pilot** row shows its button as it reads, such as `Resolve #N`, then the prompt it sends, and says `default` or `custom` at its right (`custom` when either is your own), the selected one before its **Edit** button. `e`, enter or **Edit** opens one editor with a **Label** and a **Prompt** field, on **Prompt**; `↑`/`↓`, tab or a click go to the other field. Enter or **Save** saves both in one write, and only what changed; with neither changed, nothing is written. A label or prompt that can't be saved shows why under its own field, and then neither is saved. **Use default** and ctrl-r empty only the field you are on. `d`, `R` and `V` on a button's row say it isn't a profile. The profiles file's format is unchanged by this editor: labels and prompts saved before show in the editor as they are.
- The panel keeps the width you drag it to ([#16](https://github.com/luongnv89/rex-extensions/issues/16)). It no longer sets its width back to 36 columns when a pane opens or closes in its tab, and it opens at that width again, also after Rex restarts. The width is kept in `~/.local/state/rex-github/width` on the machine the panel runs on, at most half the panel's split. Resizing Rex's window saves no width. Until you drag it, the panel opens 36 columns wide, about the width of Rex's sidebar.
- Resolve and Review open the agent's pane to the right of your agent, side by side (a vertical split), instead of below it.

- **Behavior change:** with no profile assigned, Resolve and Review start Claude Code through `mcc run`, instead of the same kind of agent as the one in your tab. Assign a profile to keep using another agent. The panel no longer needs an agent in the tab: with none, the new pane opens beside the pane the panel follows. When it looks for your agent, the panel recognises `claude`, `codex`, `gemini`, `opencode`, `pi`, `vibe` and `devin`; `gemini` isn't a harness a profile can start.

### Fixed

- A profiles file saved by a newer rex-github now says so, instead of only that its version isn't one the panel reads ([#69](https://github.com/luongnv89/rex-extensions/issues/69)). A panel started before rex-github was updated keeps the old code, so it refused to save a file a newer panel had written, as "The profiles file is version 7, not 1, 2, 3, 4, 5 or 6: it is read only here". It now reads "The profiles file is version N, saved by a newer rex-github than this panel, which reads up to version M: update rex-github if needed, then close and reopen the panel to edit it. Until then it is read only here". The file is still read only there and never overwritten; any other version it can't read says what it did before. A change refused because the file is read only says why once, as "Not saved: …", instead of also repeating the same warning under it.
- The panel works in a session on a remote host. The action ran `node` with this machine's full path to `panel.js`, which doesn't exist on the remote host, so the pane closed at once. It now passes the path relative to `$HOME`, and the remote host finds `panel.js` under its own `$HOME`: install the extension there at the same path under `$HOME` ([#12](https://github.com/luongnv89/rex-extensions/issues/12)). The pane starts in the folder of the pane it opens beside, or in its machine's default folder when that can't be read, instead of this machine's clone of the extension.
